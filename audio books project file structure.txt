ReadWise AI — Full Project Plan

Project title: ReadWise AI – Intelligent Book-to-Audio and Visual Learning Assistant

Project goal: Develop a full-stack web application that accepts PDFs, images, and cloud links, converts written content into English audio, explains images and diagrams, and uses AI to help users understand, summarize, analyze, and learn from their content.

The plan below combines all the features discussed so far, including your existing book-to-audio project, free/lightweight AI models, Google Drive integration, file uploads, image explanation, accuracy improvement, sentiment analysis, and decision extraction.

1. Complete application overview

Module 1 — Input and document management

Accept files from a user's device, Google Drive, or supported online file links. Validate, organize, and process PDFs and images.

Module 2 — Text and image extraction

Extract text, headings, pages, tables where feasible, and embedded PDF images. Use OCR when a page contains scanned text rather than selectable text.

Module 3 — AI reading and audio

Generate English speech, summaries, chapter-wise reading, simplified explanations, and bookmarks.

Module 4 — Visual learning

Explain uploaded pictures, textbook diagrams, charts, and figures. Extract labels and answer questions about the visible content.

Module 5 — AI learning and analysis

Generate summaries, key concepts, flashcards, quizzes, sentiment analysis, important decisions, recommendations, and risks.

2. All input options

The application should provide three main ways to submit content.

Option A — Upload a file from the device

Supported file formats

PDF

Books, notes, textbooks, reports, scanned documents

PNG

Screenshots, diagrams, charts, scanned pages

JPG / JPEG

Photos of book pages, pictures and figures

Scanned pages

Image-based pages inside a PDF, processed with OCR

How it works

The user selects or drags a file into the upload area.

The backend checks file type, size, and whether it can be opened safely.

For PDFs, extract selectable text and embedded images page by page.

For scanned pages and images, run OCR to recognize text.

Send extracted content to the relevant AI features.

Display the extracted text and let the user listen to, summarize, or analyze it.

Useful extras: upload progress, clear error messages, file preview, page count, processing status, cancel/retry, and a delete-file option.

Option B — Google Drive link

Users paste a Google Drive sharing link to a PDF or supported image file.

Features to include

Input field for a Drive link.

Validate the link and identify the requested file.

Retrieve public/shared files when access is permitted.

For private files, offer Google sign-in and request only the required Drive permissions.

Show the file name, type, size, and processing status where available.

Report invalid links, unsupported files, expired access, and permission errors.

Important: A Google Drive URL is not always a direct-download URL. Use the Google Drive API and appropriate authorization where needed. Never ask users to make confidential files public merely to process them.

Option C — Other online links

Allow a user to paste a URL pointing to a supported PDF or image hosted on another website.

Required behavior

Validate the URL and allow only supported file types.

Download the file through the backend only after safety checks.

Reject unsupported websites, login-required pages, and links that cannot be retrieved.

Limit file sizes and download time.

Protect against unsafe URLs, including requests to private network addresses.

Never execute files or trust a URL's extension alone.

A link to a web page is not necessarily a link to the underlying file. In the first release, support direct PDF and image URLs; add other cloud services later if needed.

4. Detailed AI feature behavior
A. English text-to-speech

The system should clean extracted text before sending it to the speech engine. It should avoid reading repeated page headers, footers, broken words, or irrelevant symbols when these can be reliably identified.

Split long books into manageable sections.

Generate speech for each section rather than sending an entire book in one request.

Store the generated audio with its associated document and section.

Use an audio player with playback controls and progress.

Save the last listened-to section and position.

Suggested approach: Test a local English TTS engine such as Piper or Kokoro. Check the specific model and voice licenses before distributing the application. Keep a fallback option if a voice is unavailable on the deployment server.

B. Image and diagram explanation

Your existing notebook uses BLIP to generate basic image captions. Keep it as a baseline, but do not rely on it alone for complex diagrams. A captioning model may identify the general subject without correctly explaining labels, arrows, sequences, or scientific relationships.

The improved workflow should be:

Identify whether the image contains text, a diagram, a chart, or a photograph.

Use OCR to extract visible text and labels.

Send the image and extracted labels to a vision-language model.

Ask for a structured explanation: purpose, components, relationships, and step-by-step interpretation.

Display uncertainty when labels or relationships are unclear.

Allow follow-up questions and read the explanation aloud.

For example, a user uploads a diagram of the water cycle. The app should explain evaporation, condensation, precipitation, and how the arrows connect the stages, rather than simply saying, “This image shows the water cycle.”

C. Sentiment analysis

Use sentiment analysis to identify the tone of a passage, not to decide whether the passage is factually correct.

Possible outputs:

Positive

Negative

Neutral

Confidence score, if provided by the model

For books, sentiment can be applied to a paragraph, chapter, or selected passage. For technical textbooks, neutral may be the most common result. An optional emotion model could be added later, but it is not essential for the first version.

D. Decision and recommendation extraction

This should be a distinct feature, especially for educational materials, reports, and business documents.

The AI should extract:

Main claim: What is the author saying?

Decision or recommendation: What action or conclusion is proposed?

Supporting evidence: Which passage supports it?

Benefits: What positive outcomes are described?

Risks or limitations: What concerns are mentioned?

Source location: Page number or source passage.

Confidence or review flag: Whether the output needs human verification.

Not every book contains decisions or action items. When none are found, the application should say so instead of inventing them. Clearly separate the author's statements from the AI's own interpretation.

E. Ask questions about a document

A document Q&A assistant should answer questions using the user's uploaded content rather than relying only on the language model's general knowledge.

For larger documents, a later version can use retrieval-augmented generation (RAG):

Split extracted text into chunks.

Store searchable representations of those chunks.

Retrieve relevant passages for a question.

Generate an answer grounded in those passages.

Show page references or quoted supporting passages.

This helps reduce unsupported answers and makes the output easier to verify. RAG is a later enhancement; the initial version can answer questions from a selected page or a smaller extracted text section.

Important design rules:

Use unique IDs to connect records to the correct user and document.

Store file paths or object-storage references instead of storing large audio and image files directly in database rows.

Record the original source type, such as local upload, Drive, or direct URL.

Track model version and processing settings so you can investigate changes in output quality.

Store only the information needed for the feature; don't retain sensitive source content indefinitely without a clear reason.

Add ownership checks to every document, audio, bookmark and result endpoint.

Authentication is optional for a local prototype, but should be implemented before releasing a public multi-user application.

10. Security, privacy and reliability

These are core requirements, not optional polish.

File security

Verify actual file contents, not just extensions.

Set file-size and page-count limits.

Reject malformed or unsupported files.

Store uploads outside the public web directory.

Generate safe internal filenames instead of trusting filenames supplied by users.

Add retention limits and a reliable delete process.

Link security

Validate URLs and restrict allowed protocols.

Protect the backend against server-side request forgery (SSRF).

Block access to localhost, private network addresses and cloud metadata endpoints.

Limit redirects, download duration and response size.

Never accept arbitrary URLs and fetch them without validation.

Account and Drive security

Use secure password hashing if you implement local accounts.

Store OAuth tokens securely and request minimal Drive permissions.

Never commit API keys, OAuth secrets, passwords or tokens to GitHub.

Enforce per-user access to every document and generated file.

AI reliability

Keep the original extracted text available for verification.

Show page references for AI-generated answers when possible.

Distinguish generated explanations from source text.

Treat uploaded content as untrusted data, not as instructions to the AI system.

Tell users when OCR or image interpretation may be uncertain.

Copyright: The application should be designed for content users are permitted to upload and process. Avoid building features that bypass access controls or distribute copyrighted books without authorization.

11. Deployment and GitHub plan

GitHub will hold the source code, documentation, version history, and tests. It will not automatically run your AI models just because the code has been uploaded.

1. GitHub repository

Store the frontend, backend, README, tests and configuration examples. Exclude private keys, uploaded books, generated audio, virtual environments and model caches.

2. Frontend hosting

Deploy the React application to a suitable static frontend host.

3. Backend hosting

Deploy FastAPI to a service that supports Python dependencies, model inference, temporary storage, background tasks and adequate memory.

4. Persistent storage

Use a persistent database and suitable file or object storage. Do not assume local files on a hosted server survive restarts.

You can begin locally without paying for model inference by running compatible open models on your own machine. A public website that processes files for multiple users may require paid compute or storage, especially for image models and long audio generation. Free hosting plans often have limits, sleeping services, or insufficient memory.

Before choosing a host, benchmark the model sizes and processing time on your computer and check the host's current limits.

15. Final recommended scope

To keep the project manageable, use this as the first complete working version:

Input: PDF, PNG, JPG/JPEG, Google Drive links and supported direct file links.

Extraction: PDF text, embedded images and OCR for scanned content.

Audio: English speech, playback controls and section-wise generation.

AI: Summaries, simple-English explanations, image descriptions, sentiment, decisions and recommendations.

Interface: Dashboard, reader/audio player, AI workspace, image assistant and library.

Backend: FastAPI with separate processing services.

Storage: SQLite initially, with suitable file storage.

Models: Free/open-weight options where licensing permits, tested for accuracy and memory requirements.

Deployment: GitHub for source control, plus separately hosted frontend, backend and persistent storage.

My strongest recommendation: finish Phases 1–3 before attempting every advanced model. That gives you a working upload-to-audio application early. Then add Drive import, AI analysis and visual learning one at a time, measuring accuracy at each stage.
